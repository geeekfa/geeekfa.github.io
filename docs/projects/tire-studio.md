## One-line pitch

An internal tool that turns two reference photos (front + sidewall) of one tire model into
correct, standardized catalog images for every size in that model's line — front, sidewall,
and 45° angle — instead of photographing every single size by hand.

## Tab 1: Prepare

**What the user sees:** one button ("Render"). It reads the line's uploaded `sizes.csv` and
groups the sizes into visual clusters, then generates a base 3D render ("slick") per group.

**The problem it solves:** generating a photorealistic image per tire size is slow and costs
real GPU/AI-model time. A product line can list hundreds of sizes (e.g. "205/55R15" through
"225/60R17"), but many of them would render *visually identical* — so paying to generate each
one separately is pure waste. Prepare's job: figure out the smallest set of sizes that need an
actual render, and which other sizes can just reuse that render.

**The clever part — clustering in a scale-invariant space, not raw millimetres:**

The 3D camera in Blender frames every tire so it fills the same angle of view regardless of its
absolute size (camera distance and lens scale both derive from the tire's own radius). That
means two dimensionless ratios fully determine what a size *looks like* on screen:

- `hole` = rim radius ÷ tire radius — how big the wheel opening looks (sidewall band thickness)
- `width` = section width ÷ tire radius — how fat the tire looks

Two sizes that match on both ratios render identically no matter how far apart their real
millimetre measurements are — and two sizes that differ on either ratio render differently even
if their millimetres are close. So clustering happens in `(hole, width)` space, with a tolerance
on each axis, instead of naively bucketing by raw size numbers. This is a genuinely elegant
reframing: it turns an appearance question ("will these look the same?") into a small, provably
bounded geometry problem — the worst-case visual error per cluster is fixed by construction, not
by what happens to be in that day's CSV.

The tolerances themselves aren't guesses — they were calibrated against the real shipped
library (25 brands, 392 sizes) to land *below* the error the old naive grid-bucket approach
already allowed, while cutting the number of required renders roughly in half.

**The algorithm — greedy set cover:** picking the *fewest* reference sizes that "cover" every
size in the list is the classic NP-hard set-cover problem. Rather than reaching for something
exotic, the implementation uses the standard greedy approximation (repeatedly pick the
reference that covers the most still-uncovered sizes) — a well-known, provably-good-enough
approach (~ln(n) of optimal) instead of over-engineering an exact solver for a problem where
"pretty good and fast" is what the business actually needs. Ties break deterministically (CSV
order), so the same input always produces the same clusters — important for a pipeline other
stages depend on. After references are chosen, each size is then reassigned to its *nearest*
allowed reference (not just whichever one happened to cover it first), tightening visual
accuracy at zero extra render cost.

**Engineering hygiene worth noting:**
- Pure, dependency-injected design (`TireSizeParser` and both tolerances are injected, not
  hardcoded) — swappable without touching the clustering logic itself.
- Format-aware: metric and flotation-notation sizes never share a cluster, because the physical
  render geometry (bead ledge, ring gap) genuinely differs by format — the algorithm respects a
  real physical constraint, not just a numeric one.
- The result is a JSON contract (`clusters.json`) other pipeline stages (45° tile generation,
  label placement) rely on — with explicit guarantees in the code comments (groups partition
  the input, a reference is always a member of its own group, sorted output).

**After clustering — Blender slick generation runs as a background job:** once the groups are
known, every *unique reference size* that doesn't already have a base 3D render gets one,
generated by a Blender subprocess per missing size. This is slow (Blender is not instant), so it
never blocks the UI request — it runs as an API background task with progress polled from a
status file on disk (no database table needed; status is derived purely from what's on disk,
the same pattern the rest of the app uses for "is this thing done yet"-style state).

**What this shows about Salman's engineering (for the portfolio narrative):**
- Turns a fuzzy "will these look the same" question into a precise, boundable geometric problem
- Picks the right-sized algorithm for the job (greedy set cover) instead of gold-plating
- Calibrates tolerances against real production data, not arbitrary constants
- Keeps state management dead simple (file-existence-derived status, no extra DB tables)
- Separates fast/synchronous work (clustering) from slow/async work (rendering) correctly

## Tab 2: Front

**What it does end to end:** takes one raw reference photo of a tire, standardizes it, cleans
and repairs it, then fans it out into a finished catalog image for *every size in the line* —
7 sub-steps, `Prepare → Fit Tire → Clean → Retouch → Enhancement → Factory → Size Pack`.

### 0. Prepare
Same "whiten + AI upscale in one ComfyUI call" idea as Prepare in the other tabs: any raw photo
gets background-whitened and AI-upscaled in a single pass (never two, see below), then fit and
padded onto a square canvas. Interesting constraint: Front works natively at **1024²**, not
2048² like Sidewall — because the AI edit models used later all sample at 1024, so preparing a
2048 master just meant every later step silently shrank it and re-grew it, measurably erasing
the finest tread details and doubling the rubber grain into "coarse sandpaper." Rather than
patch around it, the fix was to match the master resolution to what the model actually samples
at, and do the *one* real upscale to catalog resolution (2048) at the very end, in Size Pack.

### 1. Fit Tire
**The problem:** a photo is never shot perfectly square — the tire leans a degree or two on the
platform, so the same tire looks asymmetric (measured: its centerline drifted 39px from top to
bottom of one real photo, where a proper render doesn't drift at all). Fit Tire renders a 3D
"slick" (from Blender) at the exact size the user typed, uses its outline as the target shape,
and warps the photo to fit it — so every master leaves this step on a known, standardized,
mirror-symmetric outline, no matter how the original photo was framed.

**Why this is a genuinely hard geometry problem, solved carefully rather than approximately:**
- The photographed tire and the rendered mask differ for **two separate reasons**, and only one
  is a defect: (a) they're literally different sizes (user photographed one tire, typed a
  different target size) — a real proportional difference that needs a straightforward per-axis
  stretch; (b) the photo itself has a slight lean — an actual defect. Conflating the two and
  fixing both with the same "radial warp" caused a real, shipped, user-visible bug: straight
  tread grooves came out visibly wavy, because the correction for a global size difference (which
  needs a uniform stretch) was fighting with the correction for lean (which needs an angular
  correction) in the same formula. The fix was to separate them: subtract out the clean per-axis
  size difference first (in closed form, using the *statistical spread* of the shape rather than
  its bounding box — because a single stray tread block touching the image edge can throw off a
  bounding box by tens of pixels but barely nudges a standard deviation), and only then apply a
  radial correction for the genuine lean. Measured result: groove waviness dropped from 19px of
  bend down to 3px.
- A second, independent bug showed up after that fix — some tires came out *pinched* in one
  spot. Root cause: a photographed outline is a fundamentally messier curve than a clean 3D
  render (sharp corners where the render has round ones, tiny serrations from tread blocks,
  even stray green-screen fringe pixels from the photo background removal). Blindly matching the
  warp to every one of those tiny irregularities dragged them all the way into the tire's
  interior, denting the tread. Solution: smooth that correction (average it over a small angular
  window) before applying it — but smooth it in a way that can only *add* a little extra size
  margin, never *subtract*, because a slightly-oversized tire silently crops back to the correct
  outline (free), while a slightly-undersized one leaves visible background gaps (not free, and
  the actual failure mode being guarded against).
- Two separate "how far off was this" numbers are computed and logged per run — one for the
  raw lean, one for the proportional stretch — specifically so a bad-looking result can later be
  diagnosed as "the photo was crooked" vs. "the user typed an unlikely size for this photo,"
  instead of a mystery.
- Several fancier alternatives (a full elastic warp method called Thin Plate Spline; correcting
  rotation as its own separate step) were actually built and benchmarked against the simpler
  shipped approach, and measurably didn't do better once the smoothing fix above was in place —
  so they were left out. That's a mark of real engineering discipline: not skipping the
  comparison, but not keeping complexity that a measurement proved unnecessary either.

### 2. Clean
An AI edit pass that erases dirt, dye lines, scuffs and discoloration, and repaints the tire a
single flat neutral grey. Deliberately runs **before** Retouch (this order was flipped once,
on purpose) — because tread damage like bent grooves or broken blocks is basically invisible on
a dirty, mottled dark tire; only once it's a uniform light grey can the geometry actually be
seen (by both the AI and a human checking the result).

### 3. Retouch
A second, separate AI edit pass focused purely on tread *geometry* — bent groove edges, uneven
depth, broken or incomplete blocks — explicitly not texture. Splitting "fix the surface" (Clean)
and "fix the shape" (Retouch) into two single-purpose passes, instead of one prompt trying to do
both, was itself a deliberate fix: one combined prompt gave the AI model contradictory
instructions on the same pixels and it handled that inconsistently.

### 4. Enhancement
A manual, brush-painted spot-repair tool sitting between Retouch and Factory, for one-off fixes
the automated passes didn't catch (e.g. one bad shoulder, one torn block) — paint the exact
damaged area, describe what it should look like, render, and either keep or discard the result,
repeatable for as many rounds as needed. Uses a hand-painted brush mask rather than a
geometric shape specifically because AI inpainting rewrites *everything* inside a mask — a loose
rectangular or ring-shaped mask would damage healthy rubber around an irregular tear, so the
mask needs to hug the actual damage tightly. Only the exact painted region is ever written back
onto the image, so nothing outside the paint can drift or soften, even across many repair rounds.

### 5. Factory
A final AI edit pass that evens out the rubber compound's overall finish, without touching tread
geometry — the "paint finish" pass after the "body work" passes.

### 6. Size Pack
Fans the single finished master out into one image per size listed in the CSV, refitting it into
each size's own correct outline, and writes these as the **final** catalog files (there's no
separate "labeling" step for Front, unlike Side and 45° — this step's output is the finished
product). This is also where the one real upscale to full 2048² catalog resolution happens,
plus a straightening pass (the master is auto-corrected for any residual tilt) before the
per-size fan-out, so a slightly crooked original photo doesn't put a repeatable lean into every
single size derived from it.

**A concrete, measured example of why several of these small corrections compound:** on one real
master, skipping the tilt-correction step left a **48px** drift in the final image; applying it
after the earlier Fit Tire step (which mostly already removes the tilt, but not perfectly) cut
that residual drift to **7.5px**. Each step is deliberately conservative on its own, and the
measured payoff comes from getting several of them right in sequence.

### What this tab shows about Salman's engineering
- Diagnoses subtle visual bugs (wavy grooves, pinched shapes) back to their root geometric cause,
  not just symptom-patches them
- Separates genuinely different problems (size difference vs. lean; surface vs. geometry) into
  independent, single-purpose steps rather than one step trying to do everything
- Builds and *measures* fancier alternatives before ruling them out — decisions are backed by
  numbers, not gut feel
- Designs corrections to fail safe (favoring a harmless "slightly oversized, gets cropped" over a
  visible "gap" defect)
- Logs diagnostic numbers (deskew angle, warp factors) specifically so a bad result later has a
  traceable cause instead of being a mystery

## Tab 3: Side

**What it does end to end:** takes one raw sidewall photo, standardizes it, restores/cleans it,
rebuilds the wheel-opening edge to match the user's own reference photo, and fans it out into a
finished, size-labeled catalog image for every size in the line — 9 sub-steps:
`Prepare → Retouch → Clean → Wipe Bead → Add Bead → Enhancement → Factory → Size Pack → Label Pack`.

### 0. Prepare
Same idea as Front's Prepare (whiten + AI-upscale in one combined pass, run exactly once), plus
one thing unique to Side: an optional **rotation** slider, applied to the raw upload *before*
anything else, so a sidewall photographed at an angle can be squared up first. Runs natively at
2048² here (vs. 1024² on Front) — deliberate, because the bead-ring geometry and the arc-text
placement later in this tab are calibrated at that resolution; the doc explicitly flags this as
"a legacy exception, not a precedent" so nobody "unifies" it with Front by mistake.

### 1. Retouch
An AI edit pass that sharpens and deepens the sidewall's moulded relief and texture bands —
purely enhances, erases nothing.

### 2. Clean
Erases unwanted text/markings the user draws an arc around, one region and one round at a time.

### 3. Wipe Bead
Detects the wheel-opening ("bead") ring automatically, lets the user nudge its exact position
with sliders, then paints that band pure white — clearing the way for a fresh one to be built.

### 4. Add Bead
Rebuilds the bead ring to match the user's adjusted annulus, using a 3D-rendered reference —
this step is gated on the 3D engine (Blender), not the AI image engine, and can't be canceled
mid-run. **A neat design decision here:** rather than re-rendering a new 3D ring on every slider
nudge, the system renders *one* canonical ring shape once and caches it, then mathematically
warps (polar-remaps) that cached render to fit wherever the user draws the annulus — separating
"the expensive 3D work" from "the cheap interactive fitting," so live adjustment stays instant.

### 5. Enhancement
Same brush-painted, multi-round, Keep-it/Discard spot-repair model described under Front, reused
here — paint the exact area, describe the fix, iterate. **Clean (step 2) and Enhancement (step 5)
share the exact same underlying mechanism** — one masked-editing engine reused for two different
jobs (erasing text vs. general repairs) rather than two separate, duplicated implementations.
The only real difference: Enhancement also temporarily *rotates* the image so embossed lettering
faces upright for the AI model to read correctly, then un-rotates after — Clean skips that,
since erasing a mark has no "upright" requirement.

### 6. Factory
Recolors the sidewall to a matte dark charcoal and relights it evenly, leaving lettering, tread
and texture untouched. **A real, instructive bug lives here:** an earlier prompt asked for a
"uniform" surface with "no tonal variation" meaning to ban blotchy discoloration — but the AI
model read "uniform" as also meaning "smooth," and sanded off the sidewall's genuine fine mold
texture (which is visually a very slight tone difference) along with the actual defects. The fix
was precision in the instruction itself: splitting one ambiguous bullet into a `Colour` rule
(even tone, no blotches) and a separate, explicit `Texture` rule protecting the micro-relief —
a good example of a subtle, easy-to-miss AI-prompting bug traced to its exact cause and fixed
surgically rather than by trial and error.

### 7. Size Pack
Fans the finished (unlabeled) master out into one image per size via a mathematical radial
remap — pure geometry, no AI needed for the remap itself — then runs each resulting tile through
one more AI sharpening pass. Nothing here is written to final output yet; these are still
intermediate, unlabeled tiles.

### 8. Label Pack
Embosses each size's own text (e.g. `165/65R14 79T`) as moulded rubber lettering along an arc,
producing the actual final catalog image. This is the step with the most refined design
thinking in the whole tab:
- **The text placement is drawn once, reused for every size.** The user draws where the text
  band goes on *one* reference tire (as an arc with four numbers: inner/outer edge, start/end
  angle), and because those numbers are stored as *fractions* of the tire's own geometry rather
  than absolute pixels, the exact same drawing correctly maps onto a 13-inch wheel and a
  17-inch wheel alike — one manual setup covers an entire product line, not one setup per size.
- **No manual font-size control** — instead, the text is mathematically fit to completely fill
  the drawn band's actual thickness, shrinking automatically if a size's text string happens to
  be longer. This is a deliberate design choice specifically so text can never overflow onto the
  tread or rim — a structural guarantee rather than something that has to be checked per size.
- **Refinement over time, tracked and reasoned about explicitly:** the placement system started
  as 4 numbers describing a simple concentric ring, but the shared drawing tool it's built on
  lets a user move, tilt, or even flatten that arc into a straight line — which 4 numbers alone
  can't fully describe (the docs record that two earlier attempts to force-fit that richer shape
  back into 4 numbers actually shipped as bugs). The eventual fix sends the *actual drawn shape*
  itself (96 sampled points along each edge) alongside the 4 numbers, so what renders is always
  exactly what was drawn — while the 4-number form is kept as a human-readable summary and a
  fallback for older saved styles. This is a good example of iterating past "good enough,"
  catching that the abstraction was silently lossy, and fixing the actual model rather than
  patching around it again.
- **A "never guess" safety rule:** an earlier version of this step would silently fall back to
  a default/incorrect placement if it couldn't properly measure the drawn band — which, because
  this same style gets stamped onto *every size in the line* in one batch, meant a single bad
  measurement could quietly mislabel an entire product line. The fix explicitly removed every
  fallback path: if the geometry can't be measured, the render is refused outright with a clear
  reason shown to the user, rather than producing a plausible-looking but wrong result.

### What this tab shows about Salman's engineering
- Reuses one general mechanism (masked iterative AI editing) for two different features (Clean,
  Enhancement) instead of duplicating similar logic
- Separates expensive, cacheable work (the one-time 3D bead-ring render) from cheap, interactive
  work (fitting it live to user input) for a responsive UI
- Traces a subtle AI-prompt failure (an ambiguous word erasing real texture) to its precise root
  cause and fixes it with a scoped, minimal change
- Designs the sizing/placement math so entire classes of bugs (text overflow) are structurally
  impossible, rather than caught by validation
- Explicitly prefers a hard failure with a clear reason over a silent, plausible-but-wrong
  result, especially once a mistake can propagate across an entire batch of output
- Iterates past a shipped design once it's proven to be silently lossy, rather than living with it

## Tab 4: 45°

**What it does end to end:** takes the finished Front and Side output plus the 3D reference
render, generates a photorealistic 45°-angle catalog shot per cluster, cleans it up, optionally
touches it up, and stamps each size's own text onto it — 4 sub-steps:
`Size Pack → Remove boundary lines → Enhancement → Label Pack`.

**Why this tab renders per-cluster, not per-size:** this is the direct payoff of the Prepare
tab's clustering work — generating a photorealistic 45° image is the most expensive step in the
whole pipeline, so instead of ~33 renders (one per size), the line only pays for ~5 (one per
visual cluster); every other size in that cluster reuses the same tile pixel-for-pixel and only
its own embossed text differs.

**A deliberate, physically-motivated camera choice:** the 3D reference render for this tab uses
a *different*, longer-lens camera than the one Front Studio uses. At a 45° angle the tire
extends significantly toward the viewer in depth, comparable to the camera's own distance from
it — a wide, close camera (correct for Front's flat-on shot) would balloon the near sidewall and
warp the rim opening into a fisheye at this angle. This was tested and measured, not assumed.

### 0. Size Pack
A guided, one-cluster-at-a-time flow: pick an AI engine, its prompt loads automatically, pick a
seed, render. Feeds the cached 3D slick render (with deliberate green/yellow guide lines still
visible — kept on purpose as visual landmarks the AI model anchors the angle to) together with
the finished Front and Side images into the chosen engine to produce one unlabeled 45° tile per
cluster.

**Multiple interchangeable AI engines, each with real, measured trade-offs:**
- Some engines (Flux-based) work by *masking* — they literally copy over the untouched pixels
  from the 3D reference and only regenerate the necessary parts, which means they can't drift
  from the reference's geometry, camera angle, or exact proportions.
- Other engines (the "Nano Banana"/Google family) regenerate the *entire* frame rather than
  compositing — which produces different results but can't structurally guarantee it preserves
  the reference geometry. This surfaced as a real, observed defect: the model would occasionally
  **mirror-flip the whole tire** (a tire photographed leaning 45° left came back leaning 45°
  right) — a subtle failure mode because a mirrored tire is still "the same shape," just wrong.
  The fix that measurably helped: explicitly telling the model in the prompt that the two guide
  lines from the reference image must land in the exact same place in the output — anchoring two
  concrete landmarks turned out to drag the model's sense of overall orientation along with them.
- Two of the engines call Google's image-generation API directly instead of going through the
  local AI-workflow engine — architected as a genuinely separate code path (own client, own
  availability check) so a missing Google API key fails cleanly without affecting the other
  engines, and vice versa.

### 1. Remove boundary lines
A focused, single-purpose AI pass that erases the green/yellow guide lines Size Pack deliberately
left in — a clean example of *not* over-loading one AI call with two jobs (generate the angle,
AND make it presentable): generation gets a clear landmark to anchor to, cleanup happens once,
separately, afterward.

### 2. Enhancement
The same "paint the exact area, describe the fix, iterate with Keep-it/Discard" model used in
Front and Side, reused again here — but with one important twist: the mask isn't a simple ring,
because a tire viewed at 45° in perspective is not a circle — it's closer to two independent,
irregular, non-concentric curves. So the paintable mask is built directly against the actual
rendered geometry of that specific cluster's tile, not a generic circular guess. Rotation used
here is purely a *view* convenience (so the user can see upright text to paint over accurately)
and is fully undone before anything is saved — the stored tile is always at its original angle.

### 3. Label Pack
The most technically involved step in the entire project, doing for the 45° view what Side's
Label Pack does for the flat sidewall — except the underlying geometry is much harder, because
at this angle the tire's inner and outer visual edges are genuinely different, irregular curves,
not two circles or ellipses that share a center. Several early, simpler models for this ("just
fit two matching ellipses," "describe it with one center point and a tilt") were tried and
explicitly rejected once measured against real renders, in favor of directly sampling both
curves point-by-point and always working from *that*, keyed by angle, so a point on the inner
curve and its matching point on the outer curve are always known and travel together.

**Genuinely fine typography engineering, each decision backed by a real measurement:**
- Letters stand upright from the tire's inner edge (like real moulded rubber lettering does),
  sharing one common foot-line — an earlier, simpler approach that centered each letter on the
  midline instead left every letter's "foot" sitting at a visibly different height.
- Each letter's rotation follows the true local direction of the curve it's standing on, not a
  cruder approximation — the difference was measured directly: the simpler approximation turned
  letters through only 66° of a 72° arc span where the correct answer needed the full 87°,
  visibly under-rotating text toward the ends of a curved word.
- Spacing between letters is based on each letter's actual inked width, not the font's built-in
  spacing metrics — because font metrics are tuned for ordinary paragraph text, where a
  character like "1" reserves much more blank space around itself than a character like "/". On
  a real size label this made gaps between characters vary by **342%** — wildly uneven — while
  switching to ink-based spacing brought that down to under 2%.
- No manual "font size" control at all — like Side's Label Pack, type size is derived
  automatically from the available band thickness at each letter's own position, so it always
  fits and never overflows, by construction rather than by later validation.

**A pattern of catching and fixing an entire class of subtle bugs, not just one instance:** this
step went through several real, user-reported rounds of "the text lands in the wrong place after
I move or reshape the drawing" — each traced back to the same root cause: the user is allowed to
freely move, rotate, and reshape where the text band goes with a general-purpose drawing tool,
but the system was internally storing that placement as a small, fixed set of numbers (like
"center point + tilt angle") that simply *cannot* represent an arbitrarily moved or reshaped
band — so converting it back and forth silently lost information and the text drifted from where
it was actually drawn. The eventual, durable fix: stop trying to compress the drawn shape into a
small parametric summary at all, and instead store and reuse the *exact drawn curve itself*
(sampled as a dense set of points) end to end — the small parametric numbers are kept only as a
human-readable summary and as a fallback for older saved data. And, learning from how long that
class of bug kept resurfacing in slightly different forms: a hard safety rule was added so that
if the system ever again can't precisely measure the drawn shape, it now refuses to render at all
with a clear on-screen reason — rather than silently falling back to a wrong-but-plausible
placement, which is what let the earlier versions of this bug slip through unnoticed until a
size label showed up in the wrong spot on a finished catalog image.

### What this tab shows about Salman's engineering
- Makes a real, physically-justified engineering trade-off (long-lens vs. wide-lens camera) based
  on the actual geometry of the problem, not convenience
- Directly exploits earlier work (Prepare's clustering) to cut the cost of the most expensive
  step in the pipeline by roughly 6-7×
- Evaluates multiple third-party AI engines on their actual, measured failure modes (mirroring,
  geometry drift) and designs prompts/architecture around each one's specific weakness
- Rejects an appealing-but-wrong simplification (ellipse/parametric fitting) once real
  measurements showed it didn't match reality, in favor of a more direct, sampled representation
- Systematically hunts down a recurring *class* of bug (lossy shape representation) to its true
  root cause instead of patching each new symptom separately
- Turns "we keep almost fixing this" into a structural guarantee (refuse to render rather than
  guess) once the same failure mode had resurfaced enough times to prove it needed one

## Tab 5: Publish

**What it does end to end:** the finishing tab — it never generates any new pixels, it only
takes what Prepare through 45° already finished and packages it for delivery. 2 sub-steps:
`Watermark → Export`.

**A clean architectural principle running through this whole tab:** it only reads from what the
first four tabs already wrote, and never touches or overwrites that original output — every step
here works on its own copy, so nothing downstream can ever corrupt the actual generated catalog
images.

### 0. Watermark
Only activates once a size has all three finished images (front, sidewall, 45°) — it won't
half-watermark an incomplete size. Stamps *copies* of the three finished images with both a
faint visible watermark and hidden embedded copyright/artist metadata (the kind that survives
even if someone crops the visible mark out) — the originals are left completely untouched, the
stamped copies live in their own separate folder.

### 1. Export
Repackages the watermarked copies into whichever of three fixed output resolutions the user
checks (2048×2048, 1024×1024, 800×800 — any combination, all produced in one combined job), and
also writes a companion spreadsheet of the exported sizes alongside the images. Deliberately
**not** an arbitrary "type in any resolution you want" control — a small, fixed, known-useful set
of sizes was a conscious simplicity choice over building general resize tooling nobody asked for.
Always builds from the watermarked copies, never straight from the original output — so it's
structurally impossible to accidentally ship an unwatermarked image.

### What this tab shows about Salman's engineering
- Keeps a hard, one-directional data flow (generate → watermark → export) where each stage only
  reads the previous stage's *own* output — never the raw original — so a mistake in packaging
  can never contaminate the actual generated artwork
- Resisted building unnecessary flexibility (arbitrary export resolutions) in favor of the fixed
  set that's actually used — a deliberate YAGNI call, not an oversight
- Designed the gate (all three angles required) so nothing incomplete or half-finished can ever
  be exported by accident

## Overall pipeline — one thread through all 5 tabs

Looking at Prepare → Front → Side → 45° → Publish as a whole line, a few things stand out as
consistent engineering habits, worth calling out once at the top level (and maybe as the
portfolio page's closing "what this all adds up to" section):

- **Cost-consciousness baked into the architecture itself**, not bolted on: clustering (Prepare)
  exists specifically so the most expensive step (45°) runs ~6-7× less often than naively
  possible, and every step's resolution/upscale choices are tuned against measured, real
  quality/speed trade-offs rather than "bigger is always better."
- **Every non-trivial numeric decision is backed by a real measurement**, on real production
  data, and often literally recorded (pixel-error tables, before/after numbers) — this shows up
  in the tolerance calibration, the deskew/warp comparisons, the AI-prompt wording fixes, and
  the typography spacing fix.
- **A recurring discipline of tracing a bug to its true root cause, and fixing the model, not the
  symptom** — most visible in Front's Fit Tire warp bugs and 45°'s Label Pack placement bugs,

- **Safety-first defaults once a mistake can propagate widely**: several steps (Label Pack in

- **Single-purpose steps over multi-purpose ones**: nearly every tab splits what could have been
  one AI instruction into several narrow, single-verb passes (Clean vs. Retouch vs. Factory) once
  a combined instruction was shown to confuse the model — a pattern repeated independently across
  three different tabs.
